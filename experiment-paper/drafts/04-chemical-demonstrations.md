# 4. Chemical-Process Modelling Demonstrations

This section demonstrates specification-management behavior on chemically meaningful models. The geothermal power-loop flowsheet is the main example because it combines heat transfer, pressure-changing equipment, connected process streams, and a recycle. The dynamic tank and Ahuora material are deliberately narrower: they illustrate, respectively, the scope of indexed Replacements and the use of explicit metadata by a graphical client. They are not presented as separate numerical-performance evaluations.

## 4.1 Geothermal-Heated n-Butane Power Loop

The geothermal demonstration is a steady-state geothermal-heated n-butane power-loop flowsheet. Its implementation constructs pump and turbine units, recuperator, preheater, vaporiser, and condenser heat exchangers, and a water mixer. The n-butane stream is connected from the condenser through the pump, recuperator, preheater, and vaporiser to the turbine, then through the recuperator and condenser. On the water side, the vaporiser outlet joins an auxiliary-water stream in a mixer before entering the preheater. The flowsheet uses Helmholtz property packages for water and n-butane and expands Pyomo network arcs into equality constraints.

The baseline Specification interface distinguishes the roles of the quantities used to define the units. The project heat-exchanger model registers overall heat-transfer coefficient and area as `design` Canonical Variables, with pressure drops also registered as `design` Canonical Variables when pressure change is enabled. The pump and turbine models register mechanical work as an `operation` Canonical Variable and efficiency as a `design` Canonical Variable. Unconnected inlet-port variables are registered as `inlet` Canonical Variables after flowsheet connections have been created. In the experiment implementation, the recycle circulation rate is treated separately as a loop anchor because it has no unit owner.

The resulting interface allows a study to state an observed or requested outlet condition while preserving the baseline Specification count. For example, the current replacement-enabled geothermal script replaces the condenser overall heat-transfer coefficient with a variable representing the condenser shell outlet temperature, then fixes that temperature to 274.970330261. The corresponding heat-transfer coefficient becomes a Guess Variable. The implementation reports the resulting specification state and checks that the whole model has zero counted degrees of freedom before initialization. This does not establish that every such target is feasible or that the model will solve; it makes the exchange and its retained guess explicit.

The broader geothermal example in the existing paper source identifies analogous physically interpretable exchanges: heat-exchanger outlet enthalpies can replace overall heat-transfer coefficients, and pump or turbine outlet pressures can replace mechanical work. Outlet enthalpy is used there instead of outlet temperature for the specified heat-exchanger conditions. These exchanges support a design-oriented question such as calculating heat-transfer coefficients from selected outlet conditions, while retaining the normal fixed-design configuration as the baseline. The variables must still be selected so that the resulting model is structurally acceptable and physically appropriate.

## 4.2 Initialization of the Geothermal Configuration

The geothermal model contains a recycle, so its initializer uses Pyomo `SequentialDecomposition`, chooses a tear set heuristically, and supplies tear guesses from the destination-port variable values. In the replacement-enabled version, the sequence runs while `replacements_suspended_in(fs)` is active. Unit initialization therefore proceeds with Canonical Variables fixed and replacement variables released. After the sequential initialization pass, the code solves the flowsheet in that suspended state, checks for optimal termination, and exits the context. Exiting restores the requested Replacement configuration; a final solve is then performed with the target replacement variable fixed and the released Canonical Variable acting as a Guess Variable.

This sequence separates the initialization configuration from the final study configuration. It is useful because the unit initialization routines can rely on the baseline Canonical Variables, but it is not evidence that the replacement mechanism universally improves initialization or numerical robustness. Failure remains possible at the canonical initialization solve, the restored study solve, or because of infeasible targets or inadequate guesses.

## 4.3 Dynamic Tank: Indexed-Replacement Scope

The prior dynamic-tank demonstration provides a scoped example of how the same interface applies when variables are indexed over time. It describes a steam tank represented by an IDAES heater with constant volume, inlet and outlet valves, and a PID controller that targets tank outlet pressure through the inlet flow. In that formulation, valve opening fraction and flow or pressure quantities may be time-indexed, whereas valve coefficient is constant. A Replacement between time-indexed variables exchanges equal-sized indexed collections of fixed states; it is not interchangeable with a scalar variable solely because both are conceptually related.

The described tank configuration uses an outlet-pressure target in place of an inlet-flow Specification and a PID setpoint in place of a valve-opening Specification. During initialization, the released inlet flow is available as a Guess Variable; after the canonical configuration is initialized, the target outlet pressure is fixed and the flow is recalculated. The project implementation likewise treats an indexed variable as all fixed or all unfixed and rejects partially fixed indexed variables. This is a capability demonstration of consistent fixed-state bookkeeping for indexed variables, not a claim of dynamic-model validation or a general proof for all dynamic discretizations.

## 4.4 Ahuora as a Metadata Client

The Ahuora Digital Twin Platform material provides an example of how an application can consume explicit specification metadata. Its documented backend uses IDAES and Pyomo. In the interface description, fixed Canonical Variables, Guess Variables, and calculated variables are displayed differently; when a user requests a Replacement, the client can show both the variable being fixed and the Canonical Variable it releases. The paper source illustrates a compressor in which outlet pressure replaces mechanical work while isentropic efficiency remains fixed, allowing mechanical work to be entered as an initial guess and then calculated on solve.

This example is evidence that the interface supplies provenance that another client can present. It is not a usability study, does not establish improved human usability, and should not be used to claim that the graphical interface has been evaluated here.
