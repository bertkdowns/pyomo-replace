\renewcommand{\PaperAbstract}{%
Equation-oriented process models can be reused for different studies, but their equations rarely identify which inputs are ordinarily fixed or which input should be released when a new target is imposed. We present \texttt{pyomo-replace}, a Pyomo/IDAES framework that records ordinary inputs as Canonical Variables and exchanges them one-for-one for alternative Specifications through tracked Replacements. A released Canonical Variable retains its value as a Guess Variable, and the baseline Specification set can be temporarily restored for initialization. We demonstrate the approach on a geothermal power loop and evaluate it in constrained AI-agent specification tasks on three process flowsheets, with one recorded session per condition. In the geothermal and heat-integration cases, where direct workflows required multiple patches, replacement used fewer patches, less time, and fewer tokens; the no-guess geothermal direct workflow also failed to report optimal termination. In the milk-evaporator case, every workflow reported optimal termination after one patch, and replacement showed a small time and code-size overhead relative to direct fixing. These proof-of-concept results suggest that the interface has a modest adoption cost but can reduce repeated correction when direct specification is difficult.}

\section{Introduction}
Equation-oriented models (EOMs) provide a common set of first-principles equations for design, performance-rating, and operating studies \cite{shacham1982equation,biegler2010nonlinear}. Algebraic modelling languages (AMLs), including Pyomo, and process-model libraries such as IDAES make these models composable from reusable blocks \cite{hart2011pyomo,lee2021idaes}. However, their variables and equations do not usually state which variables a component author expects a client to specify, or how that choice should change with the study intent.

For example, a pump may be specified by mechanical work in a performance-rating calculation, but by outlet pressure in a measured-condition study. A heat exchanger may be specified by its heat-transfer coefficient in one study and by an outlet thermal condition in another. In a conventional AML workflow, either change is a collection of low-level operations: fix one variable, unfix another, provide initial values, and assess the resulting formulation. The relationship between the physical target and the released quantity is left in scripts, comments, or modeller knowledge.

This is an interface problem rather than only a variable-counting problem. A degree-of-freedom (DoF) diagnostic can identify an under- or over-specified formulation, but cannot say which Specification is semantically appropriate to exchange, why it was exchanged, or how the altered model should be initialized. This information is important when components are composed into flowsheets and when graphical clients, workflow tools, or coding agents specify a supplied model.

We present \texttt{pyomo-replace}, a framework to manage which variables supply the Specifications in a Pyomo/IDAES EOM. The framework makes a baseline Specification set explicit through \emph{Canonical Variables}, and represents an alternative Specification as a tracked \emph{Replacement}. The contribution is a software interface that gives users a starting point for specifying a flowsheet assembled from predefined unit operations without requiring intimate knowledge of every underlying equation. Replacements preserve substantial flexibility in selecting alternative Specifications while enforcing a one-for-one exchange and structural check. We demonstrate the interface on a geothermal power loop, then evaluate it with an AI coding agent on prepared chemical-process flowsheets.

\section{Background and Related Work}
\subsection{Equation-Oriented Models and Composition}
Equation-oriented flowsheeting represents coupled process units as a simultaneous equation system, avoiding a fixed calculation order and supporting large nonlinear simulation and optimization problems \cite{shacham1982equation,biegler2010nonlinear,dowling2015framework}. AMLs provide a declarative layer over that system: symbolic variables and constraints can be indexed, manipulated programmatically, and grouped into hierarchical components rather than assembled directly in a solver representation. In Pyomo these components are Blocks, which can contain reusable equations and nested components; IDAES builds on them with process unit models and property packages \cite{hart2011pyomo,lee2021idaes}.

Composition adds another interface. Pyomo Network collects related variables in Ports, connects compatible Ports with Arcs, and expands those Arcs into algebraic equality constraints \cite{pyomoNetworkDocs}. In an IDAES flowsheet, a Block commonly represents a unit operation, while its inlet and outlet Ports expose the variables used to connect that unit to the rest of the process. These abstractions allow a modeller to assemble a larger equation-oriented model without interacting directly with every equation inside each unit.

This has resulted in a rich ecosystem of reusable unit models, property packages, and flowsheet templates. However, intended use is not always evident from equations and model structure alone; modellers rely on documentation, degrees-of-freedom analysis, and structural diagnostics to determine how to specify an unfamiliar unit. This is partly because of the flexibility inherent in equation-oriented modelling: for example, a pump may be specified by mechanical work in one study, outlet pressure in another, and pressure ratio in a third. A standard interface is difficult to define when the appropriate Specification changes with study intent.

\subsection{Specification, Diagnostics, and Initialization}

Model diagnostics are standard tools for understanding the behaviour of an unfamiliar unit model. For a model with variables $x$, active equality constraints $c(x)=0$, and fixed variables, a useful operational count is
\begin{equation}
  \operatorname{DoF}_{\mathrm{count}} = n_x - n_c - n_f.
\end{equation}
This count is a valuable assembly diagnostic, but zero counted DoF does not prove independent equations, structural nonsingularity, physical feasibility, or numerical convergence. Incidence analysis and Dulmage--Mendelsohn decomposition can locate structurally under- and overdetermined subsets, while Jacobian-based tools address numerical pathologies that a scalar count cannot reveal \cite{bunus2001debugging,parker2023dulmage,lee2024model,allan2025jacobian}. These diagnostics identify problematic structure; they do not encode which physically meaningful variable a modeller intended to exchange or why. Process knowledge, structural diagnostics, scaling, and initialization therefore remain necessary.

Process design and operation also motivate alternative specification choices. Design and control degrees-of-freedom analysis relates process design choices to quantities that must be set or controlled in operation \cite{luyben1996design}. Process simulators expose neighboring mechanisms, such as an Adjust block that varies one quantity until another reaches a target \cite{dwsimAdjust}. Such target-seeking features solve a selected calculation, whereas the present work records the persistent relationship between a newly imposed target and the ordinary input released in its place; it is not a controller or optimization method.

Changing the fixed-variable set also changes initialization. Warm starts, decomposition, simplified models, and staged release are established ways to approach difficult nonlinear formulations \cite{SAFDARNEJAD201539,dowling2015framework}. Unit initializers are commonly written for an expected Specification set, and recycle flowsheets require propagated values or tear guesses \cite{lee2021idaes,pyomoNetworkDocs}. An alternative Specification therefore creates not only a counting decision but also a need to retain useful guesses and define an intermediate Specification set from which to initialize.

\subsection{Explicit Interfaces and Software Clients}
The framework is also related to software contracts and provenance. Design by contract argues for making component expectations and invariants part of an interface rather than leaving them to caller convention \cite{meyer1997object}. Provenance standards similarly distinguish an inspectable record of how an artifact or state was produced from the artifact alone \cite{w3cProvOverview}. We use these ideas narrowly: \texttt{pyomo-replace} does not capture complete computational provenance, but it turns a pair of otherwise independent fix/unfix calls into a queryable record with an invariant on the number of Specifications.

Repository-level coding-agent benchmarks motivate evaluating whether such an interface is usable by a software client, while also showing the need for execution-based and carefully bounded claims \cite{jimenez2024swebench}. Tool-using-agent work provides a plausible reason that constrained operations can be preferable to open-ended code changes, but does not establish that benefit for process modelling \cite{yao2023react}. The agent study in this paper is therefore an evaluation context for the specification interface, not a claim about general AI capability.

Taken together, prior work provides equations and reusable model structure, diagnostics for a selected formulation, target-seeking calculations, and initialization methods. The narrower gap addressed here is a flowsheet-owned interface that declares the ordinary set of Specifications, records an exchange when study intent changes, and makes the initialization consequence inspectable.

\section{Specification Interface}

\subsection{Framework Semantics}
A \emph{Specification} declares that a Canonical Variable, or its active Replacement, supplies one degree of freedom. A Canonical Variable is registered as the ordinary specification for its owning block and is labelled with a \emph{Specification Category}, such as inlet, operation, design, or initial condition. Registration fixes newly registered variables; after flowsheet connections are expanded, unconnected inlet-port variables can also be registered.

A Replacement substitutes a non-canonical variable for one Canonical Variable. Activation fixes the replacement variable and unfixes the Canonical Variable, which becomes a \emph{Guess Variable}: it retains a value for initialization but is no longer fixed during the requested solve. Table~\ref{tab:concepts} summarizes the visible contract. This one-for-one exchange preserves the baseline number of Specifications; it does not prove that the new Specification is suitable.

  \renewcommand{\arraystretch}{1.05}
  \begin{tabularx}{\columnwidth}{@{}lX@{}}
    \toprule
    \textbf{Element} & \textbf{Role} \\
    \midrule
    Canonical Variable & Ordinary, fixed specification registered by a block author. \\
    Specification Category & Label for specification intent, such as design or operation. \\
    Replacement & Recorded exchange: a non-canonical variable is fixed and a Canonical Variable is released. \\
    Guess Variable & Released Canonical Variable whose value remains available for initialization. \\
    Replacement Candidate & Unfixed non-canonical variable that may be requested as a Replacement. \\
    \bottomrule
  \end{tabularx}
\end{table}

The authoritative state is attached to the flowsheet, allowing a Replacement to span block boundaries while retaining one record. The implementation requires both variables to be contained by that flowsheet; the released variable to be a currently fixed Canonical Variable; and the replacement to be a wholly unfixed, non-canonical variable. It treats indexed variables atomically, rejecting partially fixed indexed variables. After an exchange, it checks the Pyomo incidence graph and restores the previous state if the Dulmage--Mendelsohn decomposition reports unmatched constraints \cite{bunus2001debugging}.

The client interface is concise:
\begin{lstlisting}[style=psecode]
specs = SpecificationState.for_flowsheet(
    model.fs
)
specs.register([
    (unit.heat_duty, "operation")
])
specs.register_inlet_ports(model.fs)
specs.replace(unit.heat_duty,
              unit.outlet.enth_mol)
\end{lstlisting}
Inspection methods report Canonical Variables, Replacement Candidates, active Replacements, and Guess Variables for a flowsheet or block.

\subsection{Staged Initialization}
The explicit relationship also supports a reusable initialization contract. During initialization, the framework can temporarily suspend the relevant Replacements: Canonical Variables are fixed and replacement variables are released. A unit or flowsheet is initialized with its expected baseline Specification set, then the requested Replacements are restored and the model is solved again. This lets the released Canonical Variable act as a Guess Variable with a retained value without requiring each unit initializer to enumerate every valid alternative Specification. It remains a workflow convention, not a convergence guarantee.

\section{Geothermal Demonstration}
The main demonstration is a steady-state geothermal-heated $n$-butane power loop comprising a pump, turbine, recuperator, preheater, vaporizer, condenser, water mixer, and recycle. It uses Helmholtz property packages for water and $n$-butane. Heat exchangers register overall heat-transfer coefficient and area as design Canonical Variables; the pump and turbine each register mechanical work as an operation Canonical Variable and efficiency as a design Canonical Variable. These declarations expose the ordinary inputs contributed by each reusable unit model rather than requiring the flowsheet author to recover them from its equations.

Flowsheet composition determines the remaining Specifications. Arcs constrain connected inlet variables from upstream outlets, so intermediate streams do not require independent conditions. After the Arcs are expanded, the framework registers only unconnected process and utility inlet variables. Together with the unit-level declarations, these variables provide a complete baseline set of Specifications from which a client can begin, reducing the trial-and-error of selecting enough fixed variables across the assembled flowsheet.

\begin{figure}[htp!]
  \centering
  \includegraphics[width=\columnwidth]{../../paper/assets/geothermal-replacement.drawio.png}
  \caption{Geothermal power-loop example. A study target can replace a baseline Canonical Variable while retaining an explicit record of the exchange.}
  \label{fig:geothermal}
\end{figure}

The executable replacement-enabled case fixes a condenser shell outlet temperature of 274.970 K in place of the condenser overall heat-transfer coefficient. The coefficient becomes a Guess Variable. With the coefficient fixed, the same condenser equations can rate installed equipment and calculate its outlet condition; with the temperature fixed instead, they calculate the coefficient required to meet that thermal target. No unit equation is reformulated. The same pattern allows an outlet enthalpy to replace a heat-transfer coefficient in an exchanger-design study, or an outlet pressure to replace pump or turbine work when the downstream pressure is known.

Figure~\ref{fig:geothermal} makes the intent of each change visible: the physical target is recorded together with the ordinary engineering input released in its place. Thus a specified outlet pressure is distinguishable from an independently fixed stream property, and the client can see that mechanical work is to be calculated. The model retains the flexibility of choosing alternative Specifications while preserving the reason for each choice.

The recycle is initialized using Pyomo sequential decomposition and tear-stream guesses. The sequence first suspends Replacements, initializes and solves with the baseline Specification set, restores the requested Replacements, and finally solves with the requested Specification set. The released heat-transfer coefficient acts as a Guess Variable with a retained value, so the ordinary unit initialization procedure can be reused rather than rewritten for the outlet-temperature Specification. This example demonstrates an explicit change of study intent and reusable initialization; it does not imply that all target values are feasible or that all Replacements initialize successfully.

\section{Agent-Assisted Specification Evaluation}
\subsection{Method}
We evaluated whether an explicit specification interface makes a constrained coding task easier for \texttt{gpt-5.6-terra}. Each clean OpenCode session received a Markdown scenario and a prepared Python template with topology, diagnostics, initialization, and solve routines. The agent could edit only \texttt{specify\_model}, was prompted once without human follow-up, and was asked to run the model until it solved according to the scenario.

The direct template required \texttt{var.fix()} calls. The replacement template exposed Canonical Variables, examples, replacement diagnostics, and the staged initialization contract; it required a Replacement before fixing a non-canonical variable. A second direct condition allowed approximate \texttt{set\_value()} guesses. The experiment therefore compares complete workflows, not the isolated causal effect of replacement metadata. It covers a geothermal power loop, a water-only heat-integration and steam-generation flowsheet, and a three-effect milk evaporator with mechanical-vapor-recompression recycles. The prepared templates constrain the task to specification, rather than open-ended model construction.

From each exported session, we recorded duration, token usage, patch count, and cumulative lines added and removed. Token usage is the sum of input, output, and reasoning tokens and excludes cache reads. A patch is one recorded \texttt{apply\_patch} call. Net lines is the cumulative number of additions minus removals across those patches, rather than a final-file size difference. There is one session per condition, so the observations have no uncertainty intervals and should not be treated as a performance distribution.

\subsection{Results}
Table~\ref{tab:results} reports the session-level results. Each patch records a revision to \texttt{specify\_model}. The geothermal direct workflows required two and eight patches, and the two-patch run did not report optimal termination; replacement reported optimal termination in one patch. Heat-integration required eight and ten patches for the direct workflows but two for replacement. In these sessions, lower patch counts coincided with substantially lower times and token usage, consistent with less search where direct fixing required repeated revision.

The milk evaporator provides the contrasting easy case: every workflow reported optimal termination with one patch. Replacement was slightly slower than both direct workflows, used effectively the same tokens as direct fixing, and added two net lines. This is consistent with a small cost for declarations and for learning a project-specific interface that cannot be assumed to have appeared in the model's pretraining data, although the experiment does not isolate the cause. In the two cases where direct workflows required repeated correction, replacement instead had the lowest patch count, duration, and token use.

\section{Discussion and Conclusions}
\texttt{pyomo-replace} makes specification intent an explicit interface. Canonical Variables define the baseline contract; Replacements record the new physical target and the Canonical Variable retained as a Guess Variable. Clients can inspect this Specification state without changing equations or solvers.

The study suggests that the interface's value depends on task difficulty. Replacement reduced patches, time, and tokens where direct specification required repeated revision, and reported optimal termination where the no-guess geothermal direct workflow did not. The one-patch milk case instead exposed a small adoption cost whose value depends on reducing correction in harder Specification tasks.

There was one session per condition, one agent model, prepared templates, and varying OpenCode versions. Replacement metadata, diagnostics, examples, and staged initialization were absent from direct templates, so their effects cannot be isolated. Patch count indicates repeated editing but is not a validated measure of difficulty or correctness. The results do not establish general AI capability, human usability, or numerical robustness; preserving counted DoF likewise does not establish nonsingularity, feasibility, or convergence.

The observed tradeoff supports accepting modest interface overhead to constrain harder Specification tasks and provide provenance and reusable initialization. Future work should use repeated, difficulty-stratified cases and ablate each interface feature.
